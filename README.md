# WordPress Playbook

How I build, deploy, secure and maintain WordPress sites. These are the decisions, the reasons behind them, and a starter you can clone.

It is distilled from production work: client sites on a self-managed VPS, marketing sites on WP Engine, and the forensic clean-up of compromised installs. It is also a starter: clone it and you have a working Composer-managed site. Every example has been made generic. No client, server or incident in here can be traced back to anyone.

## Principles

1. **Git is the only way code reaches a server.** WordPress core, plugins and themes are pinned in Composer. Dashboard installs, updates and file edits are disabled. Anything installed by hand disappears on the next deploy.
2. **Only our own code lives in the repo.** `src/` holds the theme, plugins and config. Everything else is built.
3. **No secrets in Git.** Configuration is committed; secrets come from a `.env` outside the docroot, or from the host.
4. **Every deploy shows a dry run first.** The deploy only writes code directories, never uploads or the host's files. A rollback is `git revert`.
5. **Production is real; local mirrors it.** Use a production database dump locally, but never copy the uploads: a local-only redirect serves missing files from production.
6. **Deny by default.** For example, the uploads folder serves an allowlist of file types and nothing else.
7. **Verify at runtime, not by reading code.** A change is done when it has been seen working in a real browser, with numbers.
8. **Plan before code, and only what was asked.** Explore, plan, get a "go", implement, verify, report.

## Quick start

```bash
git clone https://github.com/lickybuay/wordpress-playbook.git mysite && cd mysite
composer install                 # WordPress + plugins into wordpress/, then copies src/ in
cp .env.example .env             # database credentials, salts, WP_ENV=local
mysql -u root -e "CREATE DATABASE mysite CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci"
cd wordpress && valet link mysite --secure
wp core install --url=https://mysite.test --title="My site" --admin_user=admin --admin_email=you@example.org
```

Details, including importing an existing site instead of a fresh install, are in [04 — Local environment](docs/04-local-environment.md).

## Layout

```
composer.json          pinned core, plugins and themes; `composer build` copies src/ into wordpress/
.env.example           secrets template (the real .env is git-ignored)
.deployignore          what a deploy never uploads
src/
  wp-config.php        committed config with no secrets
  wp-content/
    themes/mytheme/    starter theme
    mu-plugins/        must-use plugins: WordPress loads every file here automatically
      local-uploads-from-production.php
                       OPTIONAL. Only on your local copy: an image or file that is not
                       in your local uploads folder loads from production instead, so
                       you never have to copy gigabytes of uploads. Does nothing on any
                       server. Set your local host and production URL at the top, or
                       delete the file if you copy the uploads locally.
                       See docs/04-local-environment.md.
manual-plugins/        paid plugin zips, installed as Composer packages
server/                files that go on the server by hand (uploads/.htaccess allowlist)
.githooks/             pre-commit: fixes staged PHP to the WordPress standard
tests/                 smoke tests (curl) and a WP-CLI test harness
.github/workflows/     deploy workflows, OFF until you set the DEPLOY_TARGET variable
docs/                  the playbook
wordpress/             generated by composer install (git-ignored); never edit it
```

## Deploy workflows are off by default

Both workflows in `.github/workflows/` skip every job until the repository variable `DEPLOY_TARGET` is set (Settings → Secrets and variables → Actions → Variables):

- `self-hosted`: your own server with a self-hosted runner. Use this **only on a private repository**.
- `wpengine`: WP Engine through the SSH Gateway.

Each workflow lists the secrets it needs in its header. See [03 — Deploy](docs/03-deploy.md).
