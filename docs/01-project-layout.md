# 01 - Project layout

The whole site, core included, is described by one `composer.json` and rebuilt from scratch on every deploy. The repository holds only the code we write. Everything else is pinned, downloaded and copied into a generated folder.

Why: a WordPress install that people edit in place drifts. Nobody knows which plugin version runs where, a dashboard update can break production at 5 pm, and a compromised site can keep a backdoor in a folder nobody reviews. With Composer, "what runs in production" is a commit you can read, diff and revert.

Related: [config and secrets](02-config-and-secrets.md), [deploy](03-deploy.md), [local environment](04-local-environment.md).

## Layout

```
composer.json          Pinned core, plugins, themes and translations; the `build` script
composer.lock          Exact resolved versions (commit it; generated by your first `composer install`)
.env.example           Template for the secrets file (see 02)
auth.json              Credentials for private Composer repos (git-ignored, you create it)
manual-plugins/        Zips of paid plugins that have no Composer repository (see its README)
src/                   Only our code
  wp-config.php        Committed config, no secrets (see 02)
  wp-content/
    themes/mytheme/    Starter theme: replace it with yours
    mu-plugins/        Our must-use plugins (local-uploads-from-production.php)
    plugins/           Our own plugins (create it when you need it)
wordpress/             GENERATED by `composer install`, git-ignored: the webroot
vendor/                GENERATED, git-ignored: Composer's own packages and dev tools
```

This repository is a working starter: clone it, run `composer install`, and `wordpress/` is a complete site. See [local environment](04-local-environment.md) for the Valet and Docker quick starts.

`composer install` puts a full WordPress in `wordpress/` and downloads plugins and themes into `wordpress/wp-content/`. Then the `build` script copies `src/wp-content/` and `src/wp-config.php` on top:

```json
"scripts": {
  "build": [
    "[ -d src/wp-content ] && cp -R src/wp-content/. wordpress/wp-content/ || true",
    "[ -f src/wp-config.php ] && cp src/wp-config.php wordpress/wp-config.php || true"
  ],
  "post-install-cmd": ["@build"],
  "post-update-cmd": ["@build"]
}
```

After editing anything in `src/`, run `composer build` to refresh `wordpress/`. The full file is [composer.json](../composer.json) at the repository root, and the ignore rules are in [.gitignore](../.gitignore).

The root `composer.json` requires only free packages, so it installs with no credentials. The private-repository and zip examples below are snippets to add when you need them. `require-dev` holds the coding-standard tools (`wp-coding-standards/wpcs` and the installer that registers it with PHP_CodeSniffer) and `brainmaestro/composer-git-hooks`, which installs the pre-commit hook (`extra.hooks`). The `install-hooks` script runs only when `vendor/bin/cghooks` exists, so `composer install --no-dev` in CI does not fail.

## Rules

1. **Never edit `wordpress/`.** It is overwritten by the next build. Change `src/` or `composer.json`.
2. **The dashboard cannot install or update code.** `DISALLOW_FILE_MODS` is on, so Git is the only way code changes ([why, and the other constants](02-config-and-secrets.md#hardening-constants)).
3. **Anything installed outside the repo disappears on the next deploy.** The deploy mirrors the build and deletes what is not in it. That is a feature: a plugin dropped in by hand (or by an attacker) does not survive.
4. **Pin exact versions** and commit `composer.lock`. CI runs `composer install`, never `composer update`.

## Core: `roots/wordpress`

```json
"roots/wordpress": "7.1.3"
```

`roots/wordpress` is a metapackage. It requires two others: `roots/wordpress-no-content` (a WordPress release without the bundled default themes and plugins) and `roots/wordpress-core-installer` (a Composer plugin that installs core into the folder named by `extra.wordpress-install-dir`, here `wordpress`). The version of `roots/wordpress` is the WordPress version.

**Why an exact pin and not `^6.8`:** with a range, any `composer update` for an unrelated plugin can also move core. Core upgrades should be a decision with its own commit, not a side effect. The same reasoning applies to every package below. Composer will warn that exact constraints "should be avoided"; that warning is written for libraries, not for deployments.

Keep the `extra.installer-paths` block from the root `composer.json` so `composer/installers` puts plugins, mu-plugins and themes under `wordpress/wp-content/`.

## Plugins and themes from wordpress.org

[WordPress Packagist](https://wpackagist.org/) mirrors the wordpress.org directory as Composer packages: `wpackagist-plugin/<slug>` and `wpackagist-theme/<slug>`. It is the default way to add anything free.

```json
"repositories": {
  "wpackagist": {
    "type": "composer",
    "url": "https://wpackagist.org",
    "only": ["wpackagist-plugin/*", "wpackagist-theme/*"]
  }
}
```

Add one with `composer require wpackagist-plugin/<slug>:<version>`. Commit `composer.json` and `composer.lock`.

## Private vendor repositories

Some paid plugins (Elementor Pro, Yoast Premium and similar) publish their own Composer repository. When a vendor offers one, prefer it over a zip: updates are a version bump.

```json
"vendor-private": {
  "type": "composer",
  "url": "https://composer.vendor.example",
  "only": ["vendor/premium-plugin"]
}
```

- **`only`** lists the packages this repository may serve. Without it Composer asks every repository about every package, which sends your credentials to a server that has no business knowing what else you install, and lets that server shadow a name from another source.
- **Credentials never go in `composer.json`.** They live in `auth.json`, next to it, git-ignored:

  ```json
  {
    "http-basic": {
      "composer.vendor.example": { "username": "<license-or-user>", "password": "<token>" }
    }
  }
  ```

  Keep the real file in the team's password manager.
- **CI** gets the same content from a repository secret named `COMPOSER_AUTH_JSON`. Composer reads the `COMPOSER_AUTH` environment variable directly, so the workflow only needs `COMPOSER_AUTH: ${{ secrets.COMPOSER_AUTH_JSON }}` on the install step; no file is written. See [deploy](03-deploy.md).

## Free and premium side by side: `replace` and `provide`

Several vendors ship a free plugin and a premium one that contains or extends it. If another package requires the free `wpackagist-plugin/foo` while you run `vendor/foo-premium`, Composer installs both, WordPress loads two copies of the same code, and the site dies with "cannot redeclare" errors.

Tell Composer the premium package stands in for the free one:

```json
"replace": { "wpackagist-plugin/foo": "*" }
```

`replace` means "this project already contains that package": Composer will never install it. `provide` is weaker: it only satisfies other packages' version requirements ("I offer foo 28.5") and does not stop the real package from being installed if something else asks for it. Use `replace` when the premium plugin includes the free one's code, `provide` when you only need to satisfy a dependency check.

## Paid plugins that only come as a zip

When there is no Composer repository, keep the zip in `manual-plugins/` and declare it as a `package` repository:

```json
"example-premium-zip": {
  "type": "package",
  "package": {
    "name": "your-org/example-premium-zip",
    "type": "wordpress-plugin",
    "version": "1.0.0",
    "dist": { "type": "zip", "url": "./manual-plugins/example-premium-zip-1.0.0.zip" },
    "require": { "composer/installers": "^2" }
  }
}
```

Rules:

- File name is `<slug>-<version>.zip`. The version in the name makes an old zip impossible to confuse with the new one.
- The plugin folder must be the single top-level directory inside the zip.
- The `version` and `dist.url` in `composer.json` must match the file.
- Licenses often restrict redistributing a paid plugin. Keep the site repository private, and check the license if you are not sure.

**To update one:** download the new zip, add it under its new name, update `version`, `dist.url` and the `require` line, delete the old zip, then run `composer update your-org/<slug>`.

## An in-house plugin with its own dependencies

A plugin that only has PHP files of its own needs nothing special: put it in `src/wp-content/plugins/` and `composer build` copies it. If it has its own `composer.json` with dependencies, or it is shared between sites, declare it as a `path` repository:

```json
{ "type": "path", "url": "./src/plugins/mysite-tools", "options": { "symlink": false } }
```

and require it as `"your-org/mysite-tools": "*@dev"`. `symlink: false` makes Composer copy the plugin into `wordpress/`; a symlink would point outside the build and break on the server.

## Translations

[`inpsyde/wp-translation-downloader`](https://github.com/inpsyde/wp-translation-downloader) fetches language files from translate.wordpress.org during `composer install` into `wordpress/wp-content/languages/` (core, `plugins/`, `themes/`). Configure the languages under `extra.wp-translation-downloader`. Do not run `wp language ... update` on the server: translations come from the build like everything else.

Its lock file, `wp-translation-downloader.lock`, is **git-ignored on purpose**. With a lock present the plugin skips downloads and assumes the files are committed. Here `wordpress/` is rebuilt on every deploy and is not committed, so a CI build would end up with an empty `languages/` folder.

## Recipe: update a plugin

```bash
composer outdated --direct                       # what is behind
composer require wpackagist-plugin/<slug>:<new>  # or edit the version and run:
composer update wpackagist-plugin/<slug>
composer build
```

Test it locally ([local environment](04-local-environment.md)), then commit `composer.json` and `composer.lock` together. Merging to the deploy branch is the release.

## Recipe: update core

1. Read the release notes and check that the plugins you rely on declare support for the new version.
2. Change the version in `composer.json` and run `composer update roots/wordpress --with-dependencies` (the `--with-dependencies` flag moves `roots/wordpress-no-content` with it).
3. `composer build`, then click through the site locally against a copy of the production database.
4. Commit `composer.json` and `composer.lock`. After the deploy, run `wp core update-db` if the release changed the database schema.

The versions in `composer.json` and in the snippets are examples. Pin the ones you actually run.
